# How

Use for "how does this work?", walkthroughs, runtime flow, and ownership. Use `why.md` for motivation.

1. State the best-guess scope.
2. Explore directly for small questions. For broad subsystems, split 2 to 4 read-only slices when useful.
3. Follow real calls and data. Read definitions, callers, types, tests, and config.
4. Stop when trigger-to-effect is clear.
5. Explain before critiquing architecture.

Return overview, key owners, step-by-step flow, relevant files, gotchas, and open questions. Name paths and symbols. Separate facts from inference.
